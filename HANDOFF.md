### Current development cycle — YIN octave misdetection on "e"/"o"-like vowels (2026-09-27, cloud session)

- **User-reported bug:** pitch analysis reports an octave too high on "え"/"お"-like vowels. Reproduced with a synthetic glottal-pulse vowel whose only strong formant sits at ~2x f0 (F1 ≈ 523 Hz for a target of C4/261.63 Hz): 100% of frames detected exactly one octave high. Root cause in `yinPitchTrack` (`src/engine.js`): YIN's absolute-threshold rule stops at the FIRST cmndf dip below threshold scanning from short to long lag; when a strong 2nd-harmonic/formant makes the half-period dip cross threshold on its own, it is picked before the true (longer, lower) period is ever reached. `stabilizeOctaveErrors` (a separate later pass) only repairs short isolated bursts by design and does not touch a sustained, frame-consistent error like this one.
- **Fix:** after YIN's normal tau selection, check for a deeper cmndf minimum near double the candidate; if found, treat that longer period as the true one. Gated to avoid a known pitfall: CMNDF's cumulative normalisation naturally drifts lower at longer lags on ANY clean, confidently periodic tone (confirmed by hand: a genuinely high, cleanly periodic note also gets a deeper dip at its own doubled period). The correction therefore only fires when the *original* pick is itself marginal (cmndf within half the detection threshold of crossing it) and the doubled candidate is decisively strong (absolute floor and a large relative margin) — first found via a synthetic-singer sweep that surfaced false-positive octave-DOWN corrections on confidently-detected high notes (e.g. midi 71/72/74/76 "i" vowel, midi 84 "a"/"o"/"e") before this gating was added; verified those no longer regress. Checked twice per frame (covers a rarer two-octave error).
- **Measured:** isolated reproduction (minimal single-formant glottal model, `F1 = 2×f0`) now measures the correct fundamental at every tested f0 (180/220/261.63/330/392 Hz) and vowel-formant offset swept ±5% around the octave. A/B sweep across 4 vowel shapes × 17 pitches (48–84 MIDI) on the fuller synthetic singer: 0 octave errors introduced, 0 regressed vs. the pre-fix engine, except the pre-existing (unrelated) fmax=1000 Hz boundary edge case which was already broken on main and is not worse now. Real Chromium app: loading the reproducing WAV now shows "C4" in the pitch inspector (was "C5" before the fix — confirmed against the pre-fix engine in this same session). Isolated smoothness-metric A/B (same code, only this fix toggled) shows the fix shifts (not degrades in aggregate) the boundary-continuity numbers on the demo song's own "e"-vowel note, because that note's own source pitch track — which PSOLA's grain placement depends on — was itself subtly wrong before this fix; not independently comparable to the prior cycle's numbers for that reason. `npm run qa`, both background-playback regressions, and the standalone/`file://` E2E all still PASS. New regression case in `tests/regression.js` (a minimal reproducing vowel, plus a clean-tone sweep guarding against the false-positive risk) fails on the pre-fix engine and passes now.

### Current development cycle — smooth pitch transitions (2026-09-27, cloud session)

- **Goal:** pitch changes as smooth as possible. Measured bottleneck: note boundaries, not note interiors (interior pitch error ~1-2 cents, HNR change < 1.6 dB). (1) A note's shift switched instantly at its boundary (step). (2) Every note restarted its own PSOLA grain chain, so even a uniform edit broke waveform continuity at each boundary. (3) The app's per-note local render used a different guide channel/chain than the full render, so splices clicked (exported app output measured 4.7x source curvature on main).
- **Engine changes (`src/engine.js`):** `buildShiftPlan` builds a continuous shift curve: raised-cosine transition (±60 ms, ≤30 % of each note) between touching notes (gap ≤ 30 ms) when at least one is edited and the edge pitch jump ≤ 7 st (larger jumps are usually YIN octave errors; resynthesising those with a wrong period was worse). Resynthesis runs per contiguous *region* with one grain chain; every voiced cycle in a region is resynthesised even where the curve crosses 0. 1-2-frame YIN voicing dropouts are bridged. Grain sources always crossfade the two bracketing cycles (the old nearest/bracket switch at 1.5 st measured worse). `guideChannelIndex`/`opts.guideChannel` fixes the pitch-mark channel per song; `resynthRegions` exported.
- **App changes (`src/app.js`, `src/worker.js`):** song-level `S.guideChannel` passed to every render; local render widened by the transition length and to whole overlapping regions (≤ 12 s), with a 12 ms splice crossfade as a safeguard.
- **Measured (synthetic singer with jitter/shimmer/breath/vibrato/legato/consonant/vowel changes, 44.1 kHz stereo; scripts in session scratchpad, not committed):** cycle-to-cycle waveform continuity at edited boundaries improved or equal in 6/6 scenarios (e.g. one note +2 st p5 0.878 → 0.980; uniform +3 st min 0.120 → 0.286, p5 0.765 → 0.870; breathy −3 st min 0.571 → 0.821). ### Current development cycle — edited note collapsed to silence (2026-09-25, cloud session)

- **User-reported defect:** moving a note with pitch correction destroyed its sound.
- **Root cause (reproduced in real Chromium):** `segmentToPlain()` in `src/app.js` sends segments without `durationSec`; `buildGrainSchedule()` bounded its loop with `seg.durationSec * 1700`, i.e. `NaN`, so no PSOLA grains were ever scheduled for app edits. The blend mask still switched the note to the (empty) wet signal, so the edited note became ~0.45 s of silence (energy ratio 0.002). Engine unit tests passed because they used full segment objects. Fixed in the engine by deriving the duration from `endTime - startTime`.
- **Secondary defects fixed in the same path:** (1) the feathered blend reached a few ms past the first/last grain of a note → a hole followed by a full-scale step (second-difference 25–80× the source) at edited note boundaries; the blend is now limited to the output ranges that received grains (`limitBlendToCoverage`) and mask frames are clipped to their note. (2) Overlap-add divided by a near-zero window sum on large downward shifts (zero samples between grains, octave-down kept the original pitch); division now uses a 0.5 floor, leaving upward/small shifts (overlap ≥ ~0.7) numerically unchanged. (3) Mask hop derived from frame times instead of analysis-rate `hopSize` (defensive for iPhone downsampled analysis; no audible difference measured at 2× downsampling).
- **Measured:** `npm run qa` PASS; solo/playback background regressions PASS; new regression cases (legato phrase, app-shaped plain segments, full vs chunked equality, ±2/±7/−12 st, octave-down, downsampled analysis) PASS and fail on the previous engine.
